# 스펙 문서 작성 가이드

## 목적

- 스펙 문서는 사용자가 기대하는 도메인 동작과 정책을 기록한다.
- 스펙 문서는 코드가 현재 어떻게 작성되어 있는지 설명하지 않는다.
- 스펙 문서는 이후 TC 문서와 구현이 따라야 할 기준으로 작성한다.
- 코드 수준 스펙과 구현 중 확인한 플랫폼 제한 사항은 스펙 문서가 아니라 context 문서에 분리해 작성한다.

## 작성 대상

- 사용자에게 관찰되는 기능, 화면 상태, 전환, 권한, 데이터, 플랫폼 정책을 작성한다.
- 빌드, 검증, 포맷처럼 개발자 대상 기능은 개발자가 관찰할 수 있는 빌드 계약과 정책만 작성한다.
- 현재 TODO 상태인 기능도 사용자가 관찰할 수 있는 현재 기대 동작을 명시한다.
- 특정 코드 구조, 라이브러리 API, 플랫폼 API의 구현상 제약에서만 발생하는 세부사항은 context 문서에 작성한다.
- Android/iOS처럼 플랫폼별로 나뉘는 내용도 코드나 API 차이에서 비롯된 세부사항이면 context 문서에 작성한다.
- 권한, 저장 위치, 화면 전환처럼 사용자가 관찰하는 동작이 플랫폼 정책 때문에 달라지는 경우에는 스펙 문서에 작성한다.

## Context 문서

- Context 문서는 `docs/contexts/<도메인>.md` 경로에 작성한다.
- Context 문서 제목은 `# <도메인> Context` 형식을 사용한다.
- 스펙 문서와 같은 도메인을 다루는 context 문서는 같은 파일명을 사용한다.
- 구현 과정에서 확인한 코드 수준 결정, 내부 API 계약, 모듈 경계, 플랫폼 API 제한, 라이브러리 제약, fallback 근거는 context 문서에 작성한다.
- 사용자가 관찰할 수 있는 동작이나 TC의 기대 결과가 되는 정책은 스펙 문서에 작성하고, 그 동작이 필요한 코드 수준 배경만 context 문서에 작성한다.
- Context 문서는 스펙을 대체하지 않으며, TC 문서와 구현이 따라야 할 기준은 스펙 문서에 남긴다.

## 형식

- 문서 제목은 `# <도메인> 스펙` 형식을 사용한다.
- 필수 동작은 `## 스펙` 섹션에 작성한다.
- 플랫폼별 정책, 권한 정책, 예외 조건은 필요할 때 `## 정책` 섹션에 작성한다.
- 외부 근거가 필요하면 `## 참고` 섹션에 공식 문서나 우선순위가 높은 자료를 링크한다.
- 스펙 충돌 검증 결과는 스펙 문서에 작성하지 않는다.

## 문장 규칙

- 한 문장에는 하나의 요구사항만 작성한다.
- 요구사항은 관찰 가능하고 검증 가능한 문장으로 작성한다.
- UI에 표시되는 문구, 권한명, OS 정책명처럼 도메인에서 고정된 이름은 그대로 쓴다.
- 파일명, 클래스명, 함수명, 테스트 소스셋, 내부 자료구조, 호출 순서 같은 구현 설명은 작성하지 않는다.
- 코드 구현 중 새로 확인한 제약을 스펙 문장으로 작성해야 한다면 사용자에게 관찰되는 정책만 스펙 문서에 남기고, 코드 수준 원인과 제약은 context 문서에 남긴다.
- 테스트 방법, 작업 이력, 구현 계획은 작성하지 않는다.
